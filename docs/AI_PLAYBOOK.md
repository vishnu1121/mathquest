## Historical Arena implementation

The owner then specified four AI features, and they are implemented together as the **Muddle Monster Arena** (the **Arena** navigation tab): a zero-shot Socratic AI companion, in-memory Elo adaptive difficulty, a dynamic scaffolding engine, and a procedural misconception boss system. The owner's brief named Python; the app has no Python runtime, so the Elo and scaffolding engines are pure TypeScript with the same formulas, tier rules and unit tests. The three earlier proposals further down (Teach Pip, Save the Isles and the others) remain unselected history.

**Classes (2026-09-15) left the AI features unchanged.** The owner split the game into six classes and asked to leave the AI as it is. The new class chapters generate and check their questions in code. Their “Help me think” hint uses the existing `hint` task; its facts are the question's built-in hint and the numbers in the prompt, with the answer's numbers left out. No new AI task was added.

**Hoot's hints are three steps (2026-09-17):** notice it, try one action, then see how — a worked example on different numbers for Grade 2 and up, or the method shown on the objects for Kindergarten and Grade 1, where no different example exists. The rule for the exact step now travels with each request, because a general system prompt was dropped often enough to reject good hints; a rejected reply is retried once, and only then does the child see a failure message. Guards are unchanged apart from allowing example numbers that appear nowhere in the child's own question or answer.

**First live verification (2026-09-17):** Groq free tier, `openai/gpt-oss-120b`. Real replies for coach, hint, mission and journey passed the guards; in-game Hoot gave two successive grounded hints with no answer leakage. Measured acceptance and the prompt fix it produced are in [PROJECT_STATE.md](PROJECT_STATE.md).

**The provider is configuration (2026-09-17).** `src/ai/server/provider.ts` selects Anthropic (default) or any OpenAI-compatible provider from `AI_PROVIDER`, `AI_API_KEY`, `AI_MODEL` and `AI_BASE_URL`. Every task, prompt, guard and validator below is unchanged and provider-unaware; replies are always re-checked in code. Disclose the provider and model you ship.

**Example to clarify the proposed Pip loop:** three robots each need four batteries. The child tells Pip to make a group of four for each robot. Pip visibly distributes batteries according to its interpreted plan; the child can repair that plan. A later task has five robots, so Pip must apply the same grouping strategy again. This is a proposed demo, not an implemented mission. “Remembering” would mean saved, validated strategy context; it would not retrain the model.

The previous recommendation was to start with the Pip teammate as one focused playable slice. **The owner has not accepted that recommendation.** Exact controls, action schemas, persistence, scope and model choice are still design work. A generated-world or village route remains an alternative, not an additional promised deliverable.

## Reusable implementation and missing work

- **Current foundations:** `frontier.ts` and `voyage.ts` contain code-checked constructions and solvers; `runtime/frontier-games.js` renders manipulable boards; `runtime/voyage-world.js` hosts exploration; `runtime/dream-lab.js` demonstrates cancellable generation and honest fallback labels. These can support a future slice without replacing the whole application.
- **Current API:** eight text-output tasks in `src/ai/adventure/schemas.ts`, prompts in `prompts.ts`, validators in `validate.ts`, dispatch in `/api/adventure-ai`, and client requests in `runtime/core-ai.js`. Existing `teach` accepts only a fixed mistake ID and short explanation. Existing `mission` returns a title, opening, four beats and closing. Neither returns executable actions.
- **Not built:** schemas for AI actions/boards/plans, a world-state action executor, action legality validation, generated-level acceptance/solvability checks, persistent validated strategy memory, or an AI-controlled NPC loop. There is no flagship implementation hidden behind a disabled setting.
- **Correctness boundary for any new direction:** AI may propose a plan, construction or move; code must check supported actions, quantities, legal transitions and success. Never execute generated JavaScript or allow model prose to decide correctness or award progress. Preserve independent/support evidence and bounded child input.
- **Verification still needed:** actual provider compatibility and response quality, latency, invalid plans/boards, interruptions and stale responses, offline recovery, keyboard/touch usability, and whether the child can understand the learning loop. Existing mocked narrative tests do not verify these future features.

Earlier ideas such as fictional character memory, construction explanations and personalized story detours may support a chosen design. By themselves they do not resolve the owner's request for an active main feature. The current product does not generate arbitrary executable games or a 3D world.
